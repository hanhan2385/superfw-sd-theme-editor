# 把 fw 固件集成进主题编辑器：可行性评估

日期：2026-10-20
评估对象：`app/sdedit.py`（SD 卡主题编辑器，v0.21）与 `fw/`（源码版 SuperFW 固件）

---

## 0. 结论摘要

**不建议采用"把固件跑进编辑器"这个方案。** 三条理由：

1. 它要解决的是**预览保真度**，而保真度只需要"布局规格一致"，不需要"执行真代码"。
   用一份共享规格能以大约十分之一的成本达到同样效果。
2. 它**不解决"鼠标自由编辑"**——自由度的天花板卡在固件的渲染代码里（坐标全是编译期常量），
   编辑器再怎么集成也突破不了。
3. 它会引入三个长期负担：GPL 分发义务、ARM 工具链体积、以及"编译产物与源码"的版本漂移。

**值得采用的是**：把 `menu.c` 的布局与角色映射抽成一份单一来源的规格（spec），
编辑器从它生成预览与点击热区，固件从它生成宏。这样预览不会再漂移，同时能把
"点预览上的元素直接改色"这种真正好用的交互做出来。

---

## 1. "集成"有三种含义，成本差一个数量级

用户提出"把 fw 固件集成到当前编辑器中"，实际可能指三件完全不同的事，必须分开评估：

| 含义 | 具体做法 | 主要成本 | 是否值得 |
|---|---|---|---|
| A. 渲染集成 | 编辑器内跑固件的 `menu_render`，用真渲染当预览 | 极高（仿真环境 + 外设 mock） | 不值得 |
| B. 数据模型集成 | 编辑器严格遵循固件的资源模型（颜色角色、图标槽、图片规格） | 低（已经在做） | 已经在做，需做深 |
| C. 构建集成 | 编辑器直接产出 `.fw` 固件 | 中高（工具链 / 注入点维护 / GPL） | 不建议进主程序 |

下面按 A、B、C 展开。

---

## 2. A：渲染集成——技术上能做，但性价比很差

### 2.1 硬约束：模拟器这条路是死的

项目里已经确认过：**mGBA 跑不了 SuperFW 本体**，因为固件启动要和卡带的 CPLD 做握手。
所以"用成熟模拟器跑固件截图当预览"这个最省事的方案不存在。

剩下唯一路径是 unicorn 指令级仿真，`tools/emulate_ewram.py` 已经有雏形，
但它现在只做一件事：**按真实布局跑开机流程，判断"能开机"还是"白屏"**，
不产出画面。要把它变成渲染器，需要补齐：

| 需要 mock 的东西 | 说明 | 难度 |
|---|---|---|
| FatFs + SD 驱动 | `sdtheme_load()` 会 `f_open`/`f_lseek`/`f_read` | 中：可以把文件内容直接注入，绕过 FatFs |
| 卡带模式寄存器 `0x09FFFFFE` | 每次 `set_supercard_mode` 都要应答 | 低：按写入的值记录状态 |
| VBlank 中断 / `systime()` | `menu_render` 依赖帧计数做动画 | 低：手动喂帧号 |
| DMA3（`dma_memset16` 等） | 背景填充、图标搬运全走 DMA | 中：emulate_ewram 已有 hook，但覆盖面要扩 |
| VRAM / OAM / 调色板 | 要 dump 240×160 出图 | 低 |
| 输入状态 `smenu` | 要构造"第 n 个标签页、选中第几行"的菜单状态 | **高**：这些是静态结构体，得按偏移精确摆 |

### 2.2 性能：能出图，但撑不起交互式编辑

一帧 `menu_render` 要做 34,560 字节的内容区填充、几十次文字渲染、图标搬运。
在 unicorn 里跑，即使不开逐指令 hook，单帧也是毫秒到几十毫秒级；一旦开了
内存写 hook（出图必需），还要再乘一个系数。

这意味着它**只能做"点一下按钮生成一张校验图"，做不了"鼠标拖动时实时刷新"**——
而实时刷新恰恰是"自由编辑"的体验前提。

### 2.3 最关键的一点：它并没有消除"双份真相"

即使跑真固件，链路仍然是：

```
编辑器内存模型 → sdtheme.pack() → theme.bin 字节 → 固件读取 → 渲染
```

`pack` 和固件的读取偏移依然是两份代码，只是被 `test_sdtheme_pack` 的 `#define` 对照约束着。
换句话说，**渲染集成解决的是"渲染逻辑"的漂移，但漂移的另一半在"打包格式"上，
而那部分靠现有自检已经能压住**。

本次会话里出现的两次不一致（列表行高 18 vs 16、底栏文案与图标规则）都属于
**布局常量没同步**，而不是"渲染引擎不同"。这类问题用一份 spec 就能根治。

## 3. B：数据模型集成——这才是真正该做的部分

固件对"主题"的承载力是有明确边界的，`theme.bin` v3 就是它的完整枚举：

| 维度 | 数量 | 约束 |
|---|---|---|
| 配色方案 | 6 套 | 每套 6 个角色：FG 顶/底栏、BG 内容区、FT 文字、HI 按钮边框、HIB 选中行、SH 阴影 |
| 图标 | 6 套 × 17 个 | 每个 16×16、8bpp、38 色、调色板第 0 槽恒透明 |
| 默认壁纸 | 6 张 | 240×144、8bpp、220 色（调色板槽 20..239） |
| 页面图 | 7 张 | 同上，按标签页覆盖默认图 |

**编辑器的一切"自由"都不可能超出这张表。** 这不是编辑器的限制，是固件的限制。
把这个边界明确写进 UI，比假装"可以随便拖"更诚实。

顺带一个容易忽略的点：**6 个颜色角色不是随便分的**。`reload_theme()` 除了写主调色板，
还要把它们映射到游戏内菜单（IGM）的 5 个槽位（`IGM_PAL_FG/BG/HI/SH/BL`）。
所以颜色角色一旦重命名或扩展，IGM 的配色会一起崩。

## 4. 鼠标自由编辑：能做到什么，做不到什么

这是评估里最需要说清楚的部分。逐项对照固件实现：

| 想做的操作 | 固件支持吗 | 依据 | 编辑器实现成本 |
|---|---|---|---|
| 点预览上的顶栏，改那一块的颜色 | **支持**（改 FG） | `menu_render` 用 `dup8(FG_COLOR)` 填顶栏 | 低：热区 → 角色映射 |
| 点内容区空白，改底色 | **支持**（改 BG） | 同上 | 低 |
| 点列表文字，改文字色 | **支持**（改 FT） | `draw_text_ovf` 用 FT | 低 |
| 点选中行，改高亮色 | **支持**（改 HIB） | 选中行用 63 号图标平铺，颜色来自 HIB | 低 |
| 拖动壁纸平移/缩放 | **支持** | 已有的 `CropDialog` | 已完成 |
| 点某个图标，换那张图 | **支持** | 17 个固定槽 | 已完成 |
| **拖动列表行、改行高** | **不支持** | `menu.c` 里 `(1+i)*16` 是写死的 | 需要改固件 |
| **改图标和文字的间距** | **不支持** | `render_icon(2, ...)`、文字 `x=20` 写死 | 需要改固件 |
| **调整底栏高度 / 加新控件** | **不支持** | 底栏固定 16px，页面渲染函数是 C 代码 | 需要重写 UI 架构 |
| **换字体** | 部分支持 | `fonts/` 是预生成的位图字体 | 中：要重新生成字体资源 |

**结论：鼠标自由编辑的天花板是"区域 → 颜色角色 / 图片槽"的映射，不是布局编辑。**
前者实现成本低、收益立竿见影；后者要动固件，代价见下一节。

### 4.1 如果真要做"布局自由"，代价是什么

需要把 `menu.c` 从"硬编码绘制"改成"数据驱动 UI"：

1. `menu.c` 里有 **165 处文本绘制调用、45 处硬编码坐标**（抽样统计），
   要全部改成查表渲染；
2. 需要新增一份布局描述（每个元素的 x/y/w/h、字体、对齐、绑定哪个色槽），
   按最保守估计也要几 KB；
3. **EWRAM 只剩约 21 KB**（v0.21 编译结果 235,380 B / 251 KB = 91.6%），
   布局表和通用渲染器的代码体积会很紧张；
4. 渲染循环变慢（查表 + 通用绘制 vs 直接内联），菜单本来就在 16.7 ms 的帧预算里；
5. `theme.bin` 要从"6 个固定角色"升级到"任意命名的样式表"，格式要重做（v4），
   而且要同时兼容 v1/v2/v3；
6. 游戏内菜单（IGM）用的是同一套配色槽，必须同步改；
7. 原有的"6 套主题"心智模型会被打破，老用户的 theme.bin 需要迁移。

这不是一次编辑器迭代，是**固件的 UI 架构重写**。

## 5. 现有"刻板逻辑"要不要保留

要保留，而且要保留在**数据层**，改善在**交互层**。

| 层 | 内容 | 处理方式 |
|---|---|---|
| 数据层 | 6 套 × 6 个颜色角色、17 个图标槽、7 张页面图 | **必须保留**。这是 theme.bin 格式、固件 `reload_theme()`、IGM 调色板三方绑定的契约 |
| 交互层 | 左侧"FG/BG/FT/HI/HIB/SH"六行色块 | **可以改善**。让用户在预览上点，自动选中对应的那一行，色块高亮 |
| 表达层 | 预览是 Python 复刻 | **应该改造**。由 spec 驱动，消除漂移 |

"刻板"的真正问题是**可发现性**：用户不知道"FG 就是顶栏和底栏"。解决办法不是取消角色，
而是在预览上把角色可视化出来（hover 高亮、点击选中、色块闪一下）。

---

## 6. C：构建集成——编辑器直接产 `.fw`

技术上可行，`app/fwbake.py` 已有 1,261 行、`bake()`/`rebake()`/`build_hook()` 完整实现。
但要权衡：

| 问题 | 说明 |
|---|---|
| 路线 A 的维护毒性 | 烘焙是靠"在官方固件里找内联 DMA 指令、换成 BL 到钩子"，官方固件一升级，注入点、寄存器约定、校验方式全可能变。项目已经为此反复踩坑五轮 |
| 路线 B 的工具链 | 编译 `fw/` 需要 arm-none-eabi-gcc（约 300 MB），打进 exe 体积从 21 MB 涨到几百 MB |
| GPL 义务 | SuperFW 主体是 GPL。把编译产物或源码随 exe 分发，需要同时提供对应源码和许可声明 |
| 产品定位冲突 | SD 路线的核心卖点是"刷一次固件，之后只换卡上的文件"；内置烘焙会把用户拉回"每改一次刷一次" |

**结论：不要并入主程序。** 如果确实需要"无 SD 卡也能换皮"，做成独立的小工具更合适，
且必须满足 GPL 的开源要求。

## 7. 风险清单

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| unicorn 仿真与真机行为不一致（外设时序、未定义指令） | 高 | 预览比现在还不可信 | 只在 CI 里做单帧比对，不做产品功能 |
| 双份实现继续漂移 | 现状已发生两次 | 用户对预览失去信任 | 用 spec 单一来源 |
| EWRAM 溢出（91.6% 已用） | 中 | 菜单崩溃、白屏 | 任何固件改动先看 `--print-memory-usage` |
| GPL 合规问题 | 中 | 分发受阻 | 集成前先定许可策略 |
| theme.bin 格式再次升级 | 中 | 老固件读不了新文件 | 保留版本号判断与降级路径（v3 已这么做） |
| 布局重写引入回归 | 高 | 菜单显示错乱 | 需要逐页像素比对（现在没有基线截图） |

## 8. 推荐路径

按投入产出排序，P0 先做，后面的看需要。

### P0：布局规格单一来源（1–2 天）

- 抽一份 `fw/ui_spec.json`（或生成 C 头）：页面顺序、行高、图标 x、文字 x、
  底栏高度、每个元素绑定哪个色槽。
- `menu.c` 用宏引用它（`#include "ui_spec.h"`），Python 侧 `sdedit.py` 读取同一份。
- 收益：本次会话里"行高 18 vs 16""底栏文案错"这类问题从根上消失。

### P1：预览热区点选（2–3 天）

- 用 P0 的 spec 生成一张"区域 → 色槽"的映射表。
- 预览上叠加透明热区：hover 时该区域描边 + 左下对应色块高亮；点击即选中该色块。
- 收益：把"刻板"变成"可发现"，不需要任何固件改动。

### P2：高保真校验（按需，不进产品）

- 用 unicorn 跑单帧 `menu_render`，dump VRAM 与 Python 预览做像素级比对。
- 只在发布前跑，作为回归基线，不用于实时预览。

### P3（不建议）：数据驱动 UI

- 见 4.1 的七条代价。除非产品方向变成"可换布局的主题市场"，否则不划算。

---

## 9. 最终结论

**是否值得采用：不值得。**

理由按重要性排列：

1. **收益错位**：集成固件解决的是"预览像不像"，而当前的不一致来自"常量没同步"，
   不是"渲染引擎不同"。用 spec 共享可以直接消灭这类问题，成本只有仿真方案的零头。
2. **自由度错觉**：用户想要的"鼠标自由编辑"，天花板在固件的编译期常量里。
   集成渲染不会让 `(1+i)*16` 变得可拖，只会让人误以为可以拖。
3. **长期成本**：GPL 义务、工具链体积、Arm 仿真维护、编译产物漂移，都是持续支出，
   而收益在第一天就吃完了。
4. **时机不对**：EWRAM 只剩 21 KB，任何"通用渲染器"都要在这里挤空间；
   当前固件能稳定跑，是过去多轮实机验证换来的，不适合为了编辑器体验去动它。

**该做的是**：把"固件是唯一真相"这个正确动机，用**规格共享**实现，而不是用**执行真代码**实现。
前者是把布局常量抽出来给两边读，后者是把整个运行时搬进来——同样叫"集成"，成本差十倍。
