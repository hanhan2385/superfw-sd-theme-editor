# 分支固件（`ref/superfw-fix/`）界面绘制清单 —— 哪些地方能单独设计

> 目的：把「这个固件一共画了哪些界面、每一块的底色/图片现在从哪来、还能不能单独拿出来做主题」
> 一次查清，用来决定下一版 theme.bin 加什么。
> 代码位置：`ref/superfw-fix/src/`（= r75 基线 + SD 主题改造；r78 产物在 `archive/2026-10-22/`，
> 缓存候选表已用二进制核对：`0x081F0000 / 0x081D0000 / 0x08100000`）。

---

## 0. 先记一条查出来的问题：载入画面的图是死代码

`loadrom_progress()` 里那段「借当前页的图」永远走不到：

```c
// menu.c:547
if (sdtheme_render_wall_at(frame))        // ← 恒 false
  dma_memset16(&frame[SCREEN_WIDTH*144], dup8(EX_PAL_LOADBG), SCREEN_WIDTH*16/2);
else
  dma_memset16(&frame[0], dup8(EX_PAL_LOADBG), SCREEN_WIDTH*SCREEN_HEIGHT/2);  // ← 永远走这里

// sdtheme.c:694
if (!sdt_loaded || !sdt_wall_ready || sdt_dirty || sdt_cache < 0x09000000)
  return false;                            // ← 缓存只在 0x081F0000，判据恒成立
```

两条约束互斥：chis 上 hiscratch（0x09xxxxxx）探测失败，缓存只能放 2MB scratch（< 0x08200000），
而这条守卫要求 ≥ 0x09000000。**结果：载入画面永远纯色 + 进度条**，且编辑器预览会画出壁纸
（`EXTRA_USES["loading"]` 写的也是"底图 = 当前页的图"），跟真机不符。

处理建议：不动固件（纯色其实不难看，铺图也没有安全落脚点），改**编辑器预览**和**文档**。
改动量：预览里把 loading 那屏改成纯色 + 一行说明，然后重新打包签名。

## 1. 渲染模型（决定了图片能贴在哪儿）

- 240×160，Mode 4，8 位索引色，双缓冲（`MEM_VRAM_U8[0xA000*framen]`）。
- 界面全部由 CPU 往帧缓冲里写字节；**图标/选中条是 OBJ 精灵**（`MEM_VRAM_OBJS`，1D 映射，调色板 bank 1）。
- `menu_render()` 的绘制顺序（`menu.c:2309`）决定了层次：

```
① 顶栏：dma_memset16(&frame[0], FG_COLOR, 240*16/2)        ← 恒为 FG，纯色
② 顶栏图标：render_icon(x,0, 8..14)                        ← OBJ，图标可换
③ 内容区：sdtheme_wall_enabled() ? 壁纸 : BG 纯色            ← 240×144，从第 16 行起
④ 当前页 / 当前弹窗（都画在 ③ 之上）
⑤ 诊断行（仅 SDTHEME_DIAG 构建）
⑥ alert 弹窗 + WIN0 遮罩
```

**关键事实**：只有 ③ 是「整块图片」。其余界面全是「纯色填充 + 文字 + 32 位图标」，
它们画在壁纸**上面**，所以壁纸是唯一真正意义上的"背景层"。

## 2. 调色板地图（512 项怎么分的）

| 区间 | 用途 | 谁能改 |
|---|---|---|
| 0..15 | 字体/FX 杂项（开机、图标透明色等） | 固件常量 |
| 16..19 | `FG / BG / FT / HI` | `themes[]` 前四格（每套 72 B 的前 8 B） |
| 20..239 | **壁纸专用 220 色** | 壁纸段自带调色板（440 B） |
| 240..244 | 游戏内菜单 FG/BG/HI/SH/BL | `themes[]` 后两格 + `hi_blend` |
| **245..247** | **整屏三色**（游戏内菜单底 / 载入底 / 进度条） | v5 尾部 36 B |
| 256..511 | 图标调色板（bank 1），511 = 选中条色 | 图标段 38 色 + `hi_blend` |

→ 壁纸能用 220 色，但**不能**占用 16..19 和 240..247，否则 UI 颜色会被顶掉。
这就是"壁纸文件是 34,560 B 索引 + 440 B 调色板"的原因。

## 4. 写死在固件里、但技术上能接出来的（按性价比排序）

### 4.1 顶栏图（240×16）★★★ 最划算

- 现状：`menu.c:2319` 一行 `FG` 纯色，7 个页面图标压在 OBJ 层上。
- 想加：新增 3,840 B 索引图（可共用壁纸那 220 色调色板，或自带 440 B）。
- 每套一张 = 6×4,280 = 25.7 KB；6 套共用 = 4,280 B。
- 固件改动：在 ① 之后 ② 之前插一次 CPU 拷贝（`sdt_blit` 那套，3,840 B 比壁纸小 9 倍，一帧代价可忽略）。
- 风险：低。顶栏图标是 OBJ，不会被图盖住。
- 价值：整屏观感提升最大 —— 现在顶栏永远是一条死板色，和壁纸完全不搭。

### 4.2 弹窗底色 / 弹窗框色（各 1 槽）★★★

- 现状：`draw_box_outline(frame, …, FG_COLOR)`、`draw_box_full(…, FG_COLOR, HI_COLOR)`；
  **填充用的是 HI**（和选中按钮同一个槽），**框用 FG**（和顶栏同一个槽）。
- 结果：想把弹窗做得和按钮不同色，做不到；而且弹窗是**只有框、没有底**，
  壁纸花的时候弹窗里的字直接糊在花背景上（这也是各页底部要铺一条 FG 实心条的原因）。
- 想加：`FB_COLOR`（框）+ `FB_BG`（底）两个槽，6 套 ×2×2 B = **24 B**。
- 固件改动：`draw_box_*` 换成新槽；`draw_button_box` 保持 HI（按钮仍跟 HI 走）。
- 风险：极低（纯改常量 + 改 6 个调用点）。价值：弹窗可读性 + 视觉统一。

### 4.3 各页底部帮助条颜色（1 槽）★★

- 现状：每页自己在底部铺一条 FG 实心条，行号还都不一样：
  浏览器 144..159、烧录页 144..159、设置页 140..159、关于页 138..159。
- 想加：一个 `BAR_COLOR`（6 套 ×2 B = 12 B），四处统一用它。
- 风险：低。价值：中（现在这条必须跟 FG 一样，否则和顶栏不统一，但跟 FG 一样又压不住花壁纸）。

### 4.4 游戏内菜单的 5 个图标 ★★

- 现状：**另一套独立资源** `res/icons-menu.h` —— 5 个 16×16 8bpp + 19 色调色板（1,280 B + 38 B），
  只用在这里：存档槽界面的 `M+ / M- / D+ / D-`，以及"正在存档不能进菜单"那屏的禁止图标。
- **不在 theme.bin 里**，跟主菜单那 17 个图标毫无关系，现在改不了。
- 想加：每套 1,318 B（或全套共用一份 1,318 B）。
- 难点：这 5 个图标是**编译进游戏内菜单 payload** 的常量，payload 会被 loader 搬到游戏 RAM
  的若干区域。要覆盖，得在 loader 拷贝之后按固定偏移 memcpy 进去（`menu_layout_offsets.h`
  那套偏移是 review 过的，改符号要重新核对）。比 4.1/4.2 麻烦一档，但可行。
- 风险：中。价值：中（只有存档槽界面能看到）。

### 4.5 载入画面专属图 —— 现状是死代码，先别看它 ★

- 代码路径：`menu.c:547` → `sdtheme_render_wall_at()`；画不出来就整屏填 `EX_PAL_LOADBG`。
- **实际行为：永远画不出来。** `sdt_blit` 的守卫是 `sdt_cache < 0x09000000 → return false`，
  而 chis 上 hiscratch（0x09xxxxxx）探测全失败，缓存只能落在 `0x081F0000`
  （候选表 `sdt_cand[]`，r78 二进制里已核对；诊断版底部那行 `c=81f0000` 就是它）。
  → 判据恒成立，`loadrom_progress()` 永远走 else 分支，**载入画面 = 纯色 + 进度条**。
- 想真的铺图，需要一个不会被 ROM 拷贝覆盖的落脚点：ROM 从 `0x08000000` 起往上写，
  游戏只要 >1.94 MB 就会碾过 `0x081F0000`，所以载入过程中那 35 KB 保不住；
  塞 EWRAM 也不可能（主镜像 EWRAM 已 241,512 / 251,712，只剩 10 KB 量级）。
  唯一可行的是**缩略图**（例如 60×36 = 2,160 B，4× 放大铺屏），代价不值。
- 结论：**把载入画面当纯色设计**。要改的是编辑器预览和文档（现在预览会画出壁纸，误导）。

### 4.6 选中条纹样 ★

- 现状：OBJ tile 63 在 `menu_init` 里被刷成 `SEL_COLOR` 纯色（`menu.c:2458`），
  17 个列表行用 16 个精灵横向平铺。
- 想加：16×16 花纹/渐变（256 B）。改动小，但只有"平铺条"能玩的花样有限。
- 风险：低。价值：低（除非做成半透明渐变条，那要改 BLDALPHA，风险反而上来了）。

### 4.7 游戏内菜单背景图 —— 不建议

- 现状：`ingame_menu.c:1460` 整屏 `fast_mem_clr_256(fb, dup8(BG_COLOR))`，就是一行纯色。
- 硬约束：进游戏后 32 MB 卡带 SDRAM 全被游戏占着，`sdtheme` 的壁纸缓存（0x081E0000，
  在 2 MB 写入 scratch 尾部）**必然被游戏踩掉**；34,560 B 的图没有稳定落脚点。
  要在 L+R 那一刻现读卡，得先解决"读进来放哪"（EWRAM 里挤 34 KB + 可能拖慢弹出）。
- 结论：除非专门为它做一块 EWRAM 缓冲并重新实机验证，否则不要碰。

## 5. 完全不能改的（布局 / 流程类，别浪费时间）

| 东西 | 为什么 |
|---|---|
| 七页的行高、图标坐标、底栏高度 | 编译期常量（`menu.c` 里 `26 + 22*i` 这类），`menu_layout` 只管 payload 搬运，不管版式 |
| 固件升级画面、致命错误页 | 走 `setup_video()` + `display_info_msg()`，白底黑字，刷坏了还得靠它 |
| 载入进度条的位置/粗细 | `rows 76..83`、`x=20..119` 写死 |
| 游戏画面上的"正在写入/读取"小字 | `main.c:63` 直接画在游戏帧缓冲底部，色号 `0x5` 固定 |
| 字体点阵 | 编译进 `fonts.pack` / `fonts-ext.pack`（1.7 MB），换字体等于换固件 |
| 开机白闪 | `setup_video()` 先 `dma_memset16(VRAM, 0xffff)`，是清屏动画的一部分 |

> 补一句：分支里还有个 `menu_layout` / `menu_overlay` 机制 —— 每个游戏可以在
> `hackpatches.db` 里带一个 review 过的"游戏内菜单内存布局"，用来在补丁空间紧张时
> 把菜单塞进别处。那是**给具体游戏适配用的**，不是给用户改皮肤的入口。

## 6. 编辑器预览还缺的界面（纯前端，不动固件）

现在 `EXTRA_SCREENS` 只画了 4 个：游戏内菜单、烧录 NOR、文件管理、载入进度。
固件里还有这些界面**编辑器看不到**，改配色时只能靠猜：

- 游戏内菜单的三个子界面：存档槽（`draw_states_menu`）、金手指列表（`draw_cheats_menu`）、RTC 日期（`draw_rtc_menu`）
- 固件升级弹窗（`render_fw_flash_popup`）
- 确认框（`render_popupq`，两按钮）
- RTC 日期弹窗（`render_rtcpop`）
- 存档管理弹窗（`render_sav_menu_popup`）
- 开机信息条（`display_info_msg`，白底黑字，底部 8 行）

其中"确认框"和"存档槽"最值得补 —— 它们用的是 HI 填充 + FG 框，正好是 4.2 要动的两格，
没有预览就没法验证改完好不好看。

## 7. 如果要动手：建议的打包方式

- **别一次加一格**。每加一个尾部字段就要升一次格式版本，而**老固件（r75 / v0.30）按长度整份拒绝**，
  用户必须连固件一起刷 —— 这个代价和小改动的大小无关。
- 建议一批做完再发：**4.1 顶栏图 + 4.2 弹窗两色 + 4.3 底栏色**，共用一次尾部（v7）：
  ```
  v7 尾部 = 弹窗/底栏 3 色 × 6 套 (36 B) + 顶栏图 3,840 B × 6 (23,040 B) ≈ 23,076 B
  ```
  固件侧改动集中：`draw_box_*` 换槽、`menu_render` 顶栏多一次 blit、`sdtheme` 多一段 tail 解析。
- 4.4（游戏内 5 图标）单独做一次，因为要动 payload 偏移，风险面和上面三项不在一个量级。
